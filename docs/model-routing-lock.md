# Model Routing Lock

The third-party `dsh-version-update` GUI installer is explicitly disabled in the project profile: its independent npm install, snapshot restore and automatic-update scheduler bypass the protected staging workflow. Startup verification refuses a profile that removes or re-enables that override. Until a guarded GUI implementation exists, use `scripts/update-dsh-safe.ps1` (or `node scripts/guarded-model-update.mjs --check-only <package@version>` for inspection). This also disables that plugin's settings panel and automatic updates; it does not remove its installed files or change running sessions. The profile change takes effect on normal runtime synchronization, which must not interrupt an active writer.

Core upgrades use an independent installed-code baseline at `$DSH_HOME/model-dependencies.lock.json`. It fingerprints model adapters, credential services, transport SDKs and their required dependency/peer closure, not just the versions claimed by `package-lock.json`. Approve a tested installation explicitly with `node scripts/model-dependency-lock.mjs --accept-current`. Updates first install in an isolated temporary directory with lifecycle scripts disabled; if any protected code, version or dependency resolution differs, the live installation is left untouched. A core version requiring incompatible model interfaces needs explicit compatibility work, not a silently replaced baseline. The updater does not reset this lock.

The baseline also covers native conversation execution, session admission, context compaction, title generation, cross-review, DeepSeek search and subagent callers. Every installed copy of each protected package and its dependency closure is fingerprinted, including nested copies under unrelated packages; a new nested adapter cannot silently bypass the pinned top-level adapter. Removing a protected entry point is rejected even if its dependencies remain present. This guard supports ordinary npm directory installations; linked package trees are refused rather than incompletely audited.

Both setup entry points use `npm ci` with the repository lockfile for a genuinely fresh installation, verify the source protection manifest, then create the initial local dependency baseline with exclusive creation. Existing baselines are never reset by setup. An incomplete protected installation or an existing unapproved dependency tree is refused before npm runs; use the protected updater or explicitly review that installation. Setup reads only data/home paths from `.env` using Node's built-in parser, so a clone does not require dotenv before dependencies exist and does not inherit model secrets from `.env`. GitHub desktop builds run the model and upgrade-protection test suite before packaging.

Before first capture and before staged/live upgrade verification, installation preparation reproduces the reviewed empty-required-tool-call check and the existing `openai` alias for OpenAI completions. It does not modify provider configuration. Unknown adapter layouts fail before approval; upgrades retain their rollback protection. The current published adapter plus these two patches has been checked byte-for-byte against the reviewed working adapter.

`node scripts/guarded-model-update.mjs --check-only <package@version>` performs the real isolated npm installation, preparation and fingerprint validation without changing the live manifests or dependency tree. Previously installed Electron distribution assets and `path.txt` are retained during script-free upgrades only if the Electron package version is unchanged; a changed or incomplete desktop runtime is refused, not mixed with old binaries.

Upgrade staging starts with a copy of the installed tree so npm is testing an actual upgrade, not a different clean-install layout. Staging lives on the project volume. Successful promotion swaps in the exact verified dependency tree and manifests; it does not perform a second npm install that could erase local model compatibility fixes. Originals are retained until post-promotion verification succeeds and restored if promotion fails. Clean first-time setup remains a separate lockfile-based installation path.

Actual installation refuses a live DSH supervisor before invoking npm and checks again immediately before promotion. Malformed or unverifiable supervisor records fail closed; a stale record is not deleted by the updater. `--check-only` can inspect an isolated copy while the host runs, but never replaces its live dependencies. Close DSH before a real update.

After npm updates the isolated copy, the model layer is restored from the independently verified working installation, including original nested copies and local compatibility code. Only new byte-identical copies with an approved, equivalent ancestor resolution can be removed. Final validation still requires the complete original package set, code fingerprints and dependency edges; different new adapters or incompatible copies are refused. Dependency lookup is bounded to the installation root, so an incomplete staging tree cannot borrow packages from the running parent installation. Linked copy/delete targets are refused before touching them.

New dependency shadows may also be removed to restore an original edge only when the shadow did not exist in the working installation, excluding it resolves to the exact approved path, and its containing package has unchanged code with every resolved dependency already protected. Changed owners or dependencies outside the frozen closure remain a refusal. This prevents npm from silently rerouting a protected watcher to a different `readdirp` version without accepting a new model baseline.

Routine runtime sync validates the approved `llm-pi-ai` provider catalog before copying profile files. The provider catalog is fingerprinted separately from the rest of `cordis.patch.yml`, so unrelated plugin and workflow edits do not reset provider keys, endpoints, protocols, or model IDs. A mismatch in the project or installed profile stops synchronization before files are copied.

The lock intentionally contains no credentials. Keep Claude mapped to its Claude-group credential variable and Grok mapped to its Grok-group credential variable. The API URL, protocol, and TLS behavior remain part of the locked provider catalog.

Startup does not launch the legacy `config-watcher.mjs`: it silently rewrote non-Grok protocols in imported settings every two seconds, outside the protection checks. Protocol choices must remain explicit; disabling this writer does not reset any existing settings or imply previously rewritten values were restored.

Desktop npm packaging commands generate a non-secret dependency baseline from the prepared, verified build tree. It is a generated package asset, not a committed machine snapshot. A fresh desktop startup verifies that exact tree before adopting the shipped baseline with exclusive creation; existing local baselines always win and are never reset by a newer desktop build. Runtime verification also checks the shipped baseline before any first-run synchronization writes. Cloned source installations continue to establish their independent baseline through setup.

Normal calls select a model once, invoke its configured adapter, then return the result or error. There is no failure-driven provider/model switching. Web retains the core's native tool-capable adapter; pipeline text requests retain the shared ModelClient. Both read the same active provider settings and credential references and use the same transient-error classifier. Protocol adapters remain necessary; transport is not routed through a text-only client that would discard native tool calls.

Only transient connection, timeout, throttling and service failures may retry the same model once. Funding, authentication, missing-model, empty-output and invalid-request errors stop immediately, including through transport wrappers. Explicitly disabled retries remain disabled. Circular cause chains cannot hang classification. Upgrade fingerprints and dependency checks run during setup, startup and updates, not once per model request.

The installed profile has a separate non-secret baseline at `$DSH_HOME/model-routing.lock.json`. It also freezes the model-call source files independently of the repository's own manifest: a new release cannot approve its own client replacement simply by shipping new hashes. Routine upgrades preserve the provider block and installed model router even when the new repository contains an approved but different catalog; changed call code stops before synchronization. Removing the installed profile or requesting provider synchronization does not bypass this code check. Web settings and stored credentials remain local and are never copied from a release.

The independent code baseline includes the existing emitted JavaScript for protected TypeScript callers, since Web and desktop execute those files rather than the source. A replacement compiled client is refused even when its source and repository manifest are unchanged.

An intentional, reviewed code change requires `node scripts/verify-model-routing.mjs --accept-installed-code` after its source manifest and build have been reviewed. This explicit operation backs up the local lock and updates only its code fingerprints, preserving provider/router fingerprints, settings, credentials and the independent dependency lock. Legacy local locks lacking code fingerprints require this one-time review rather than silently accepting whichever release happens to run first. Normal setup, startup and upgrades never perform this approval.

The credential initialization plugin resolves configured references through DSH's credential service. Only a missing reference may be initialized from the project's `.env`, independent of the launch working directory. Existing credentials are never replaced or borrowed from another provider group. Pipeline requests read the active profile plus current Web settings; migrated `.imported` settings cannot override an active profile.

The shared pipeline client re-resolves managed credentials and Web settings before each logical request. Child-process projections carry only a list of managed field names as provenance, never secret values in that metadata; a later request discards those projections before reading current settings. Explicit caller credentials and endpoints retain their priority. Each request keeps its own asynchronous environment snapshot through its single permitted retry, so concurrent calls cannot overwrite one another or mutate process-wide configuration. Removing a managed credential stops the next request instead of reviving a stale injected key. CLI entry points load non-secret application options rather than promoting dotenv keys above the credential store. Standalone `new ModelClient()` retains explicit environment behavior; its optional resolver supports independently managed callers.

Web request recovery has one two-attempt limit per Agent turn/step, including native provider retries. The selected model and reasoning effort remain fixed during that step's retry. Persisted failed attempts count after same-step restoration; a new turn or step starts a new limit. Non-transient failures stop even if a provider has an `always` retry policy. Provider settings are not rewritten. The source and installed router load this guard on plugin activation; an already loaded module requires reactivation or a normal restart before this change takes effect.

The Web router only selects the initial task model and preserves manual selections; it has no error-recovery handler or fallback state. Existing candidate definitions remain configuration inputs for initial selection, not a list of models to try after a paid request fails. Missing-model and unrelated endpoint 404 errors both stop without automatic retry.

For an intentional model-routing change, review the provider block, then run `node scripts/verify-model-routing.mjs --accept-current` to approve its new fingerprint. Run `node scripts/sync-dsh-runtime.mjs --sync-model-routing` to explicitly update the installed profile. Normal startup and `npm run sync:dsh` never accept drift automatically.
